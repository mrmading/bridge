Persistent sessions, and the agents they make possible

Bridge cannot keep a background agent alive because every turn is a separate print-mode process on a connection that closes with it. Fixing that does not require the Agent SDK. It requires holding two things open.

The finding that sets the price

The claude CLI accepts multiple user turns over a stdin that stays open, and keeps them in one session. Verified directly, because the docs do not cover it: two stream-json envelopes written 25s apart returned ALPHA then BETA, two result messages, one session_id (9eeb9e86…), exit 0, empty stderr.

So Bridge already has everything it needs in the binary it already ships. The migration to @anthropic-ai/claude-agent-sdk is optional, and it buys features rather than capability.

Why it fails today

Three lines describe the whole problem.

server.ts:616Spawns claude -p fresh for every turn. Print mode: one shot, exits when the turn ends.
server.ts:679child.stdin.end() — the door is closed the instant the prompt is written, so a second turn was never possible.
app.js:1354One fetch("/api/chat") per turn, whose SSE stream closes with the turn.

A subagent dispatched inside such a turn must finish before the turn does, or it dies with the process. And even if it survived, the connection that would carry its result is already gone. That is why Bridge gets synchronous agents only, and it is why swapping the spawn layer alone would change nothing.

Worth keeping from the same file: server.ts:709-716 records that --agent is verified inert in a -p turn on CLI 2.1.259, tested with a throwaway agent whose prompt was "reply only ZEBRA". The reply came back in the main voice. The system-prompt fallback exists for a good reason.

Option A — hold the process open recommended

Keep the CLI. Change what Bridge does with it. The stream parser, the renderer, the session browser, the transcript reader and the agent index are all untouched.

  1. One child per conversation, not per turn

    Spawn on the first message with --input-format stream-json always on, and never call stdin.end(). Each later turn writes another envelope into the same stdin. The live map already keys by session id, so it becomes the session registry almost as-is.

  2. A connection that outlives a turn

    Replace the per-turn SSE with one stream per conversation, opened when the conversation is and closed when it is abandoned. This is the part that actually delivers background agents: it gives a late result somewhere to land. Add a reconnect, because a laptop that sleeps must not orphan a running session.

  3. Split "stop this turn" from "end this session"

    Today /api/abort kills the child, which is correct when the child is the turn. With a persistent child, SIGINT must interrupt the turn and leave the session standing, and a separate call ends it. Add idle reaping so abandoned conversations do not accumulate processes.

  4. Move agent routing out of the system prompt

    This is the one real casualty. --append-system-prompt, --permission-mode, --model and cwd are all fixed at spawn, but Bridge re-routes to a different agent on every message (server.ts:610-615). The routing hint has to move into the user envelope instead. Changing model or working directory mid-conversation now means respawning, so the UI should either say so or start a new session.

Unverified, and worth testing before committing. Two turns proved the session holds. Not yet proven: that a subagent dispatched in turn one is still alive and reporting during turn three. That is the actual product claim, so prove it the same way — a subagent told to sleep, then a second turn sent while it runs.

Option B — migrate to the Agent SDK

Package @anthropic-ai/claude-agent-sdk, one query() per conversation in streaming-input mode: prompt takes an async generator and each user turn is yielded into a session that stays open. The process survives between yields, so an in-flight subagent can finish while the server waits.

What it buysWhat it costs
Plan mode and AskUserQuestion natively. BRIDGE_PROTOCOL currently fakes both with fenced choices blocks and a plan-card convention. Both become real. The stream parser is rewritten. The SDK emits typed messages, and deltas arrive only with includePartialMessages: true, as raw API stream events rather than the CLI's JSONL. server.ts:686-698 and the renderer in app.js both change.
A real permission surface. canUseTool(toolName, input, {signal, suggestions}) returns allow or deny, so Bridge can render approval sheets instead of running everything on acceptEdits. A second integration to keep current alongside the CLI that Bridge still reads ~/.claude for. Auth, version and update paths must agree.
Sessions are unchanged. Same ~/.claude/projects/<cwd>/<id>.jsonl, with resume, continue and forkSession. Everything Bridge built on top of the transcript files survives. AskUserQuestion is not available inside subagents yet, so a dispatched agent still cannot ask the user anything.

Recommendation

Do Option A first, and treat Option B as a separate decision made on its own merits once background agents actually work. A buys the capability you asked about with the parser and renderer intact. B buys plan mode, real permission prompts and AskUserQuestion, and it is worth doing, but it is a features project rather than an agents project, and bundling the two would hide which change broke what.

The sequencing also de-risks B: once step 2 exists, the transport already tolerates events arriving outside a turn, which is the same shape canUseTool approvals need.
